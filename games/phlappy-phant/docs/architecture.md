# Architecture

## World-space simulation

`Simulation` owns every result-changing value: the phant's height and velocity, the flap impulse, the scrolling barrels and their seeded gaps, the score, collisions, the day/night palette and the run's phases (ready, playing, dead). The phant sits at world x zero and never moves horizontally; barrels move toward it. Gaps come from a portable Park–Miller `Random`, so a seed reproduces the same course on every runtime, and the course is placed up to a fixed lookahead so a wide screen never sees an empty horizon. The simulation never reads a width: only the logical height of 352 units matters, which is what lets the renderer fill any frame without changing play. `Barrel` keeps the previous pose of each stack so rendering can interpolate between fixed steps.

`Simulation::plannedFlap` is the tool-assisted player behind the Konami code. A flap always resets the vertical velocity, so the velocity is just the number of steps since the last flap, and the planner builds, backward from a 150-step horizon (two gaps beyond the current one at the speed cap, so a position that looks safe is never a corner once the next gap comes into view), the set of hitbox positions per velocity from which some sequence of flaps no closer together than 200 ms keeps the phant inside every gap, under the ceiling and off the ground, with the barrels advanced exactly as the run will advance them. It flaps only when coasting would leave that set, so the flight stays as low and smooth as the course allows, and it keeps the first ten rows of each pass so the cost is spread over several steps. Because it never taps faster than a person can, its survival on every seeded course is the fairness proof for the speed and gap ramps.

Native PHP tests cover the generator, the idle bob, the first flap, gravity and the fall clamp, death on the ground and the settle time, seed determinism and gap bounds, scoring and the palette cadence, the speed and gap ramps, collisions against stacks and through gaps, the bindings, and the tool-assisted player surviving a minute past the speed cap without ever tapping faster than five times a second.

## Viewport-filling rendering

`Render\Scene` draws the 352-unit world at the largest whole-number scale that keeps the playable 320 units in view, anchored to the ground (a taller frame shows more sky), and derives the visible width from the frame, placing the phant at about 28 % of that width (clamped). Labels, the title wordmark and the menus use whole-number scales too, so the bitmap glyphs and tiles are never resampled. It draws the horizon band, parallax clouds, each barrel pair as stacked cap and ring tiles, the scrolling ground and the phant, whose rotation follows its vertical velocity and which tumbles when dead. Day and night blend the device clear colour and a tint over the world. The HUD uses the engine bitmap font through a cached glyph layout, every label over its own ink drop shadow so it reads on the day and night skies alike. Menus are drawn in the open sky rather than on a panel: cream pixel text with the same shadow, the selected row on a teal band behind a blinking chevron, informational rows in teal, and a themed hint line along the bottom; the scene publishes one hit region per row, which the browser mirrors as accessible buttons. Only the bindings editor, which needs value columns and text entry, uses the shared `MenuRenderer`, restyled to match.

## Browser boundary

The browser entry builds on the engine's shell services: `GameShell` claims the context, mounts the frame, measures the screen into the viewport string PHP reads every frame, runs the fullscreen machine, persists the mute and holds the status, action and bridge functions; `RegionButtons` mirrors the menu hit regions. Taps and clicks on the canvas are counted and bridged, so a flap is never counted twice through a mouse binding; keyboard and controller flaps go through the engine's editable `Bindings`. Sounds are decoded lazily by `SamplePlayer` after the first gesture and played from the status counters. The best score lives in `SafeStorage` and is reported back through a bridge for the ready screen and the result card.
